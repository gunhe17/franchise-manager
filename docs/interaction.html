point_ledger — 필드 · 용례 가이드

재무 진실(immutable)만 기록 · 워크플로는 point_requests가 담당
← datamodel.md tables.html
워크플로 상태는 별도 테이블. 사용 신청의 라이프사이클(pending → completed / rejected / canceled / reverted)은 point_requests가 관리한다. point_ledger는 완료 시점에 발생하는 재무 변동만 기록 — pending 신청은 ledger에 흔적 없음.

ledger에 행이 INSERT 되는 시나리오 5종

  • 1
    주문 적립 (credit_order)
    주문 인입 → 정책 평가 → 적립
    delta > 0 · reference_type=NULL
  • 2
    사용 완료 (debit_request)
    관리자가 외부 지급 후 "완료" 클릭 → ledger 차감
    delta < 0 · reference_type=request
  • 3
    사용 환원 (revert_request)
    완료된 신청을 사후 정정 (드물게)
    delta > 0 · reference_type=request
  • 4
    주문 취소 환원 (revert_order)
    취소된 주문의 적립을 되돌림
    delta < 0 · reference_type=ledger
  • 5
    수동 보정 (adjust)
    사고 정정·이벤트 보너스. memo + actor 필수
    delta = ±X · reference_type=NULL

핵심 원칙

  • append-only, 예외 없음 — point_ledger 모든 행 INSERT만 허용. 어떤 컬럼도 UPDATE/DELETE 불가.
  • 워크플로 분리 — 신청 진행 상태(pending/completed/rejected 등)는 point_requests에서 mutable로 관리. ledger는 재무 결과만.
  • 잔액 = SUM(delta) — 단일 쿼리. 별도 캐시 없음.
  • idempotency_key UNIQUE로 모든 변동의 재처리 안전성 확보. 특히 debit_request:{request_id}는 중복 완료 처리를 차단.
  • polymorphic 참조 (reference_type + reference_id) 2종: ledger / request. credit_order·adjust는 NULL — 정책 테이블 자체가 없으며 적립 율은 application 코드의 calculate_credit_rate 함수가 담당.
  • 적용 율 추적 — 별도 스냅샷 컬럼 없음. delta ÷ order.amount로 역산 (orders 테이블 보존 전제). 원본 주문 ID는 idempotency_key에 박혀 있음.
  • polymorphic 참조 (reference_type + reference_id) — order / request / none 3종.
  • Pending 신청 ≠ 잔액 변동 — pending은 ledger에 흔적이 없으므로 잔액에 영향을 주지 않는다. 동시 다발 신청을 admin이 선택적으로 완료.
